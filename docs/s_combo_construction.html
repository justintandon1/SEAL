Building S_combo: the math and the decisions

S_combo is the "just add the three domain vectors together" baseline that S_general gets measured against. Every number below comes from the three vectors already in the repo — no model run, no GPU — via scripts/vector_geometry.py and build_combo_vector.py.

Recipe: S_combo = rescale( Ŝ_math + Ŝ_code + Ŝ_logic ) — unit-normalize each domain vector, sum with equal weight, then rescale the sum's magnitude to match the domain vectors (their direction is untouched).

1The three ingredient vectors

Each domain vector is the SEAL contrast mean(check ∪ switch) − mean(other) — reflection/transition boundary states minus execution boundary states, layer 20, DeepSeek-R1-Distill-Qwen-1.5B — applied by adding coef × vector with coef = −1.0.

The three norms sit within 8% of each other. That closeness is why several of the decisions below turn out not to matter much — flagged as we get to them.

2How aligned are they?

Pairwise cosine similarity between the raw (un-normalized) vectors:

logic0.7610.7451.000

Stacking the three unit vectors into a 3×1536 matrix and taking its singular values gives [1.613, 0.541, 0.325]. The top direction alone explains 1.613² / (1.613² + 0.541² + 0.325²) = 86.7% of the variance — the three vectors are close to living on a single shared line, with small domain-specific residuals on top.

Why this matters for reference: Ilharco et al. (task arithmetic, ICLR 2023) found task vectors from different tasks are typically close to orthogonal — that's why summing them in weight space doesn't cause interference. These calibration vectors are the opposite: 0.75–0.89, nowhere near orthogonal. That contrast is the interesting part of the geometry story, independent of anything below.

3Decision 1 — why equal weights, not a grid search

The natural instinct is to tune weights a·M̂ + b·Ĉ + c·L̂ the way van der Weij et al. (2024) did for combining behaviour steering vectors. We tested this by fixing a = 1 and sweeping b, c ∈ {0.5, 1, 2} — a 4× ratio between the smallest and largest weight in the grid — and measuring the cosine of each reweighted combo against the equal-weight one.

Full 3×3 grid in scripts/vector_geometry.py; only the extremes are shown here.

Worst case over the whole grid: cos = 0.9847. Because the three vectors are close to rank-1 (§2), reweighting them cannot rotate the sum by much — a grid search would spend GPU budget resolving direction differences of about 0.015 in cosine.

Equal weights is also the correct comparison object, not just the cheap one. As derived in Will S_general Be the Same as S_combo?, a class-stratified, domain-balanced S_general equals the plain average of the domain vectors. Equal weights on S_combo is what makes the comparison test pooling vs. combining — the actual research question — rather than tuned vs. untuned, which would be an unfair comparison in the other direction.

4Decision 2 — why unit-normalize before summing

Two ways to combine the raw vectors:

combo_raw  = S_math + S_code + S_logic
combo_unit = Ŝ_math + Ŝ_code + Ŝ_logic     (each unit-normalized first)

These differ whenever the domain vectors have different norms — and here they almost don't:

‖combo_raw‖‖combo_unit‖cos(raw, unit)
159.4612.7930.999963
The two are the same direction. Only one needs to reach the behavioral evaluation.
This is a property of these three vectors, not a general rule. The earlier write-up (S_general vs. S_combo) shows a worked example with ‖S_math‖ = 100, ‖S_code‖ = 10 — there, raw vs. unit normalization does change the direction, because the 10× norm gap lets the larger vector dominate the raw sum. Our norms are within 8% of each other, so that failure mode doesn't apply today. We unit-normalize anyway, both because it's the more defensible default to report and because it keeps the build correct if a future domain vector arrives with a very different norm.

5The weighted-sum norm, computed by hand

scripts/vector_geometry.py reports ‖Ŝ_math + Ŝ_code + Ŝ_logic‖ = 2.7928. Here's where that number comes from — it's the vector norm expansion formula applied to three unit vectors, using the cosines from §2. 

‖a + b + c‖²  =  ‖a‖² + ‖b‖² + ‖c‖²  +  2(a·b + a·c + b·c)

Each unit vector has ‖·‖² = 1, and for unit vectors a·b = cos(a, b). So: 

‖combo_unit‖²  =  3  +  2(cos_MC + cos_ML + cos_CL)
              =  3  +  2(0.894 + 0.761 + 0.745)
              =  3  +  2(2.400)
              =  7.800

‖combo_unit‖  =  √7.800  =  2.793

Two reference points make this number legible:

If the three vectors were…‖sum‖ would be
perfectly orthogonal (cos = 0 pairwise)√3 = 1.732
identical (cos = 1 pairwise)√9 = 3.000
ours (measured)2.793
2.793 / 3.000 = 93.1% of the maximum possible norm three unit vectors could reach by summing. This is the same alignment finding as §2, restated as one number: highly aligned vectors reinforce each other on summation almost as if they were the same direction; near-orthogonal vectors would partially cancel toward √3 instead.

6Decision 3 — why the result gets rescaled

Steering applies h ← h + coef · S, so a vector's norm sets how hard it pushes the model, independent of direction. The domain vectors are applied at coef = −1.0 with norms around 56–60. combo_unit has norm 2.79.

If saved unscaled and applied at the same coefficient, S_combo would be a ~20× weaker intervention than the domain vectors. In an effect matrix, that would look almost exactly like a genuine negative result — "combining vectors barely does anything" — when really the model was barely nudged. That's a measurement artifact indistinguishable from the finding it would masquerade as.

The fix: rescale the summed direction to match the domain vectors' scale.

target  = mean(‖S_math‖, ‖S_code‖, ‖S_logic‖)
        = mean(59.666, 56.224, 55.291)
        = 57.060

scale   = target / ‖combo_unit‖
        = 57.060 / 2.793
        = 20.431

S_combo = combo_unit × 20.431      → ‖S_combo‖ = 57.060
Scaling a vector by a positive number never changes its direction — every cosine and singular value from §2–§5 is untouched. It only makes coef = −1.0 mean a comparable-sized push for S_combo as for S_math, S_code, S_logic, which is what makes the eventual accuracy/token comparison fair. This does not replace tuning α — it removes a magnitude confound from the α sweep.

build_combo_vector.py --norm can override this (unit, none, or an explicit value) if a different comparability argument is preferred later.

7Guard — the sign-convention check

Every vector must be mean(check ∪ switch) − mean(other). If one input were built the opposite way round, it would point roughly opposite the other two — summing would cancel signal instead of accumulating it, silently.

build_combo_vector.py checks every pairwise cosine before building anything and aborts if any pair is negative. Tested against a deliberately negated vector during development — it fires. All three current vectors agree in sign (§2: every cosine is positive).

What this does and doesn't answer

Settled by this page ✓ Which combination to build: equal weights, unit-normalized, rescaled to mean-source norm. No grid search needed — the direction is insensitive to weighting.
Not settled — still geometry ? Whether S_general (pooled from boundary vectors directly, not combined from the three finished vectors) lands on the same direction as S_combo. That's a single number — cos(S_general, S_combo) — available once S_general is built.
Not settled — needs behavior ✗ Whether S_combo actually steers well: accuracy and token effects on held-out benchmarks, per-problem distributions, and an α sweep. Vector-separation metrics are not a reliable predictor of steering success — geometry narrows which vector to evaluate, not whether it works.
Reproduce every number on this page: python scripts/vector_geometry.py and python build_combo_vector.py --out results/general/S_combo.pt. Both run on CPU in about a second — no model load, no GPU. See also Will S_general Be the Same as S_combo? for the algebra behind why equal-weight, class-balanced pooling and combination coincide.
