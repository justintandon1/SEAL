How the codebase fits together

Four diagrams that map the real structure: what imports what, how data flows file-by-file through the pipeline, the two parallel eval tracks, and how the orchestrator drives it all.

00

The one thing to understand first

The scripts barely call each other in code. Instead, each script writes files to disk, and the next script reads those files. So there are two separate relationship maps, and you need both:

① Code relationships (imports)

Static "who uses whose functions". Small and shallow — only a few files import each other. Diagram ①.

② Data relationships (files on disk)

The real pipeline. A .jsonl / .pt file produced by one step is the input to the next. Diagram ②.

04

Diagram ④ — What the orchestrator runs

scripts/runpod_gsm.sh is the conductor: it runs the phases in order and, crucially, skips any phase whose output file already exists (so re-runs are cheap). Time order goes top-to-bottom.

shell orchestrator phase (python script)

Config knobs are passed as env vars to this script (STEER_LAYER=20, STEER_COEF=-1.0, GSM_MAX_EXAMPLES, MAX_TOKENS) and flow down into the phase commands.
